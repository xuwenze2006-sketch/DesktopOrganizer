# 桌面刷新分阶段测量

测量日期：2026-10-13。历史计时基线为 `f959af5`，计时探针在 `c3f64e3` 提交。本次接续修正图标加载夹具，并只优化普通文件内容变化引起的共享图标失效。

## 修正后的证据与本次改动

旧夹具以 `AdvanceGeneration(int.MaxValue)` 拒绝所有图标加载请求。源码复核发现，拒绝请求还会移除 UI 的已排队标记，使后续同类型控件重复尝试入队；它改变了待测的同步工作，不能仅解释为“排除了原生图标提取”。因此，下文历史计时及阶段占比只描述旧夹具，不能据此认定正常刷新中的瓶颈排名。

当前夹具只注入冻结的非空位图，保留真实 STA 队列、请求去重、完成回调、代次/版本核验和 UI 回填。样本之间等到排队和待回填字典清空；不再拒绝请求或预填空缓存。另用暂停提取的测试确认 12 个同扩展名控件只登记一项加载，并且最终都收到同一个有效位图。

在同一套修正夹具中先复现、再修改失效规则，结果如下。这是确定性工作量证据，没有用两次单样本耗时计算加速比。

| 场景 | 修改前 | 修改后 |
| --- | --- | --- |
| 12 个 `.txt` 中修改 1 个文件内容和修改时间 | 新建 12、复用 0、新增加载 1 | 新建 0、复用 12、新增加载 0 |
| 修改时间发布 | 保持正常 | 新快照保留新时间和原 FileId，修改时间排序正常更新 |

仅在文件系统路径、非空 FileId、有效创建时间及其他身份字段均未变，且新旧修改时间有效时，普通扩展名共享图标不再失效。完整快照比较、身份发布、收件箱和规则流程仍运行。目录、`.exe/.lnk/.url/.ico`、无扩展名文件、文件替换、缺失身份信息继续使用原失效规则；手动强制刷新仍重新加载，迟到的旧代次和旧版本结果仍被拒绝。

修正后的常规回归还运行 12 项、四种扩展名的无变化、单项变化和批量改名三个场景，核对 FileId 集合与延后处理的收件箱状态。无变化和未触发缓存容量全清的单项内容变化均断言控件全复用、没有新增加载。本次没有重跑 50/200/1000 项的完整计时矩阵；后续若继续比较扫描与批量改名成本，应使用当前成功加载夹具重新采样，不能沿用旧数字作为优化后的基线。

证据位于忽略目录 `artifacts/icon-content-refresh-20261013`：`before-boundaries.trx` 记录旧规则的 4 个预期失败（3 个普通扩展名用例及 12 项实际刷新）；`after-content-rule.trx` 记录改动后的实际刷新、强制刷新、特殊图标、过期结果和排序用例。首次强制刷新用例把总加载数误当作文件图标加载数，实查发现既有流程同时加载回收站 Shell 图标；现按 `ext:.txt` 单独核对，并记录完整加载键。

本次最终验证：Release `-warnaserror` 构建 0 警告、0 错误；随后 `--no-build` 全套测试 **1360/1360 通过**，结果为 `full-final-verified.trx`。前一轮 `full-final.trx` 为 1359/1360，唯一失败是原有未提交的 `PhysicalFolderDropTests` 在 Dispose 删除临时目录时遇到 `diagnostics.log` 占用；单独复跑 `existing-test-recheck.trx` 的两个参数用例均通过，最终全套亦未再出现。该测试文件未修改，不能据复跑通过声称已修复其偶发清理问题。五个既有未提交文件 SHA-256 保持不变，未启动程序进行实机验证。

当时提出的后续方向如下；第一项已由上述成功加载夹具重新复现并实现，后两项保留为待测方向：

1. **缩小普通文件内容变化引起的图标重建范围。** 旧夹具只改一个 `.txt`，却稳定新建 13 / 50 / 250 个控件，恰为该扩展名的全部项目。源码链路是 `IconCacheInvalidation.GetCandidateCacheKeys` 将内容/时间变化传播到 `ext:.txt`，`BuildFreeIconVisualState` 又将该键的版本变化作为控件不可复用的条件。上述小规模复现已确认这个因果关系并消除可靠同一普通文件的连带失效；未据此宣称真实桌面的耗时改善幅度。
2. **随后评估批量改名的控件构建成本。** `CreateIconVisual` 会同步创建图标、标签、右键菜单及事件处理器。可以进一步拆测或试验菜单按需创建、改名后控件安全复用；目前没有单独测出菜单占比，不能直接声称菜单就是最大子项。路径和菜单闭包必须随改名正确更新。身份阶段也包含每个改名的同步诊断日志写入，不能将整段耗时都归因于身份匹配算法。
3. **无变化路径优先研究扫描中的磁盘查询，暂缓继续打磨比较和收件箱遍历。** 200 项无变化 UI 仅约 0.87 / 1.30 ms；200 项变更的收件箱协调约 0.50–1.55 ms，与控件构建相比收益有限。应先拆分扫描内的属性、分类与 FileId 读取再做修改，不能通过长期缓存文件身份牺牲可靠性。

以上历史数据只提供后续调查线索。真实桌面含分组、Shell 项、文件关联变化、自动规则、原生图标提取及屏幕绘制时的占比尚未测量，本次不声称实机卡顿已经解决。

## 历史运行方法与当前夹具差异

使用 `DesktopRefreshStagePerformanceTests`，调用实际 `RefreshDesktopSnapshotAsync`，覆盖后台扫描、Dispatcher 接收、身份/收件箱核对和同步视觉更新，不把独立函数的微基准拼成总刷新时间。

- 本机：Intel Core i7-1360P，16 逻辑处理器，约 32 GiB 内存；Windows 11 `10.0.26300`；.NET `10.0.10`，Release。
- 临时本地目录，50、200、1000 个普通文件，`.txt/.md/.csv/.pdf` 四种扩展名均匀分布；全部为自由图标，无分组或文件夹门户。固定 1920×1080 WPF 布局坐标，不涉及实际窗口显示。
- 每个规模、每个场景使用独立夹具，先建立快照，再预热 3 次、采样 9 次。正式复测分别启动新测试进程，串行运行。文件创建、内容修改、改名操作本身都在刷新计时之外。
- 无变化：重复扫描原文件；单项变化：修改第一个 `.txt` 文件内容和修改时间；批量改名：全部文件在 `Axxxx.ext`、`Bxxxx.ext` 间改名，保持 FileId。
- 25% 项目预置为延后处理的收件箱条目，验证刷新和改名后身份、条目数、延后状态与发现时间仍保留。50 项时向下取整为 12 条。
- 安全模式关闭 watcher 和自动整理；批量改名测量 FileId 回退核对路径。未调用 Show/Loaded、未启动桌面整理进程，未读写真实桌面或用户布局。
- 历史 run3/run4 通过 `AdvanceGeneration(int.MaxValue)` 拒绝加载。当前已改为 `ControlledIconLoader`，仅替换原生 Shell 图标提取，真实队列与 UI 回填继续运行。回填在样本之间排空；`refresh-total` 仍止于实际刷新任务结束，不是从开始到所有图标显示完成的端到端时长。导出 JSON 增加 `IconLoads`，记录该轮新增受控提取次数。
- 延迟保存计时器延长并在每轮结束后停止，布局写入委托仅写内存。`save-request` 只测保存请求，未覆盖后续 JSON 序列化或磁盘保存。
- 1000 项为高密度压力场景。保留网格溢出和缓存版本键超过 1024 后的全清行为，逐样本记录临时位置数、全清标记、刷新前版本键数和控件创建/复用数。
- 保留正常 GC、线程调度和系统后台活动，不强制清缓存或 GC；这些是预热后的受控测量，不是冷启动或可见桌面响应延迟。

每个样本必须到达正常完成标记。扫描不完整、异常或准备阶段提前退出均不得计为有效样本；另有负向测试验证此约束。测试不设置机器相关的毫秒门限。

## 计时与分配口径

| 阶段 | 覆盖内容 |
| --- | --- |
| `refresh-total` | 本次刷新调用总时长，包含任务和 Dispatcher 调度；跨线程只计时 |
| `scan` | 工作线程中的实际目录枚举、分类、文件属性和 FileId 读取 |
| `ui-total` | 本次 Dispatcher 回调占用时间 |
| `prepare` / `compare` | 可接受性检查 / 快照比较及运行时文件类型快照替换 |
| `icon-cache` | 缓存失效与全清 |
| `identity` | 旧身份快照复制、改名核对、布局迁移及身份更新 |
| `new-items` | 新项目识别、选择协调及新快照发布 |
| `inbox-suggestions` / `inbox` | 建议生成 / 收件箱协调 |
| `metadata` / `automation` | 组织元数据协调 / 自动整理、规则和收件箱按钮更新 |
| `visuals` | 同步视觉更新总计，包含以下四项 |
| `visuals/targets` | 清理布局、生成分组目标、排序、网格规划、自由图标目标状态 |
| `visuals/prune` | 复用判定、旧控件移除、孤立视觉清理、入口视觉维护 |
| `visuals/materialize` | 分组/自由图标控件创建、挂载和定位，以及轻桌面入口更新 |
| `visuals/finalize` | 选择样式、状态文字、按钮更新与可能的保存请求 |
| `save-request` | 刷新尾部保存请求与可选状态文字 |

同步阶段用 `GC.GetAllocatedBytesForCurrentThread` 记录分配量，不代表存活内存或全进程内存。嵌套阶段不能相加：视觉四子项属于 `visuals`，所有 UI 子项属于 `ui-total`；`refresh-total` 再包含扫描和 UI。总时长减扫描/UI的差值还包含计时、日志与调度开销，不能直接称为纯排队时间。各阶段中位数也不保证相加等于总时长中位数。

## 复现

在主线目录运行以下 PowerShell 命令，每次使用新的输出目录：

```powershell
dotnet build DesktopOrganizer.slnx -c Release -warnaserror
if ($LASTEXITCODE -ne 0) { throw '构建失败，停止测量。' }
$env:DESKTOPORGANIZER_REFRESH_PROFILE_DIR = Join-Path (Get-Location).Path 'artifacts/refresh-stage-performance/repeat-1'
try {
    dotnet test tests/DesktopOrganizer.Tests/DesktopOrganizer.Tests.csproj -c Release --no-build --filter FullyQualifiedName~ActualRefresh_RecordsThreeScenarios --logger 'trx;LogFileName=profile.trx' --results-directory $env:DESKTOPORGANIZER_REFRESH_PROFILE_DIR
} finally {
    Remove-Item Env:DESKTOPORGANIZER_REFRESH_PROFILE_DIR
}
```

每个规模输出一个包含全部原始样本的 JSON。未设置该环境变量时，常规回归只运行 12 项小夹具及计时器契约测试。生成物与 TRX 留在 Git 忽略的 `artifacts/`，不入库。

原有五处未提交修改（README、实机清单、FreeIconDrag、Workspaces、PhysicalFolderDropTests）保留在测量基线中；本次未修改这些文件。结果因此对应此本地工作区，不应宣称来自完全干净的 `f959af5` 检出。
